# rp2040-retro-dict

RP2040 掌機上的英漢／漢英電子字典，具備 1980 年代電子字典風格的合成發音。
字典資料放 SD 卡，韌體本體常駐 flash。

[rp2040-retro-handheld](https://github.com/pondahai/rp2040-retro-handheld)
生態系的一員，設計上是 [rp2040-retro-loader](https://github.com/pondahai/rp2040-retro-loader)
選單裡的另一支 `.uf2` —— 因此**最終產物必須是偏移版（連結在 `0x10004000`）**，
理由見 [docs/PLAN.md](docs/PLAN.md) §2.8。

**目前狀態：在真機上跑起來了。** 查英文、發音、注音打中文查漢英都動過。
接手請從 [HANDOVER.md](HANDOVER.md) 開始 —— 那裡有完整重建步驟與已定案事項。

## 會什麼

| | |
|---|---|
| 查英漢 | 邊打邊查，候選清單常用詞優先 |
| 查漢英 | `Fn+2` 切換，**注音輸入**（大千配列），同音字可翻頁，選字後直接查 |
| 發音 | `Fn+1`，**任何時候都唸得出東西**（見下表） |
| 顯示 | 320×240、16×16 2bit 灰階字模，中英混排；右下角是模式／大小寫／發音中 |

### 按鍵

| 鍵 | 輸入畫面 | 詞條畫面 |
|---|---|---|
| `Fn+1` | 唸反白的候選詞／打進去的字 | 唸這個詞 |
| `Fn+2` | 英漢 ⇄ 漢英 | 同左 |
| `↑` `↓` | 選候選 | 捲動內文 |
| `PGUP` `PGDN` | 注音同音字翻頁 | 跳到字母序的**前／後一個詞** |
| `ENTER` | 注音選字／查詢 | — |
| `BS` | 刪注音 -> 刪已選的字 | 回輸入畫面 |
| `ESC` | 清空 | 回輸入畫面 |
| `CapsLock` | 英文大小寫（注音模式下不作用） | — |
| `Fn+9` | 1kHz 音訊自我測試（診斷用） | 同左 |

### 發音會怎麼決定要唸什麼

| 情況 | 做法 |
|---|---|
| 英文，有音標 | 唸 `.DAT` 裡轉檔期算好的音素 |
| 英文，沒有音標（約七成詞條、還有打到一半的字） | **字母規則現場推**（`lts.c`，143 條） |
| 英文，規則也推不出（純數字、符號） | 逐字母唸 |
| 中文，字典裡有這個詞 | 唸該詞的音節 |
| 中文，字典裡沒有（例如「大家好」） | **逐字查再接起來** |

## 它跟一般的做法哪裡不一樣

三個原本被列為最大風險的問題，最後是被同一個發現一起關掉的：

- **不需要錄音**。1980 年代的電子字典是共振峰合成，不是拼接錄音 ——
  當年沒有記憶體放 1300 段錄音。那個「機器人腔」不是妥協，就是這個技術
  本身的聲音，而這正是本專案要的。
- **字典自己就附發音**。ECDICT 每筆有音標、CC-CEDICT 每筆有帶調拼音，
  轉檔期就把它們算成音素 id，韌體只拿一串 u16。
- **中英共用同一個合成器**。差別只在怎麼排共振峰軌跡，發聲機制完全相同。

結果是合成器只有約 7 KB、靜態 RAM 0，取代了原本估計的 2MB 音節庫。

後來加回了一個當初認為不需要的東西：**字母發音規則（letter-to-sound）**。
因為 ECDICT 只有約三成的詞條附音標，而且使用者打到一半的字本來就不在字典
裡 —— 要「邊打邊唸」就得在機器上當場推。它是 143 條規則、約 4 KB。

## 這個專案怎麼驗證東西

板子端唯一碰硬體的是 `RetroDict/RetroDict.ino`（螢幕、鍵盤矩陣、SD、PWM）。
**其餘全部是純 C，而且每一塊都有 PC 上的對照實作與逐筆比對**：

| 模組 | 規格 | 比對方式 |
|---|---|---|
| 查詢後台 | `tools/dictbuild/container.py` | 隨機抽數千筆，連 SD 讀取次數都要一致 |
| 排版與字模 | `tools/ui_preview.py` | 14 張畫面**逐像素**相同 |
| 合成器 | `tools/synth/` | 音高、頻譜質心、長度 |
| 字母發音 | `tools/synth/lts.py` | 字典裡沒音標的詞 + 打到一半的前綴 |
| 注音 IME | 上游碼表 | 1360 個音節全部 |
| 4bpp 畫布 | —— | 逐像素比對就是走這條路，順便驗了打包 |
| 鍵盤 | 實測真值表 | 64 格一對一，含按住／連發 |

**每一把尺都先驗過自己**：故意改壞一條規則、對調兩個聲調鍵、改一個像素，
確認比對真的會叫。這個習慣是踩出來的 —— 見 HANDOVER「最貴的教訓」。

## 編譯

**要燒進板子的是偏移版**（連結在 `0x10004000`，前 16KB 留給載入器／跳板）：

```bash
build_offset.bat [arduino-cli 的路徑] [rp2040-retro-loader 的路徑]
```

產出兩個檔案：`build_offset/RetroDict.ino.uf2` 給已經有載入器的板子（丟 SD 卡
根目錄），`build_offset/RetroDict_standalone.uf2` 前面接上跳板，可以直接 USB 燒。
封面圖會依**兩個 uf2 各自的名字**複製兩份 —— 載入器是把 `.uf2` 砍掉再接
`.RAW`（`loader/thumb.c`），名字對不上就沒有封面。腳本也會跑
`loader_offset/check_flash_layout.py` —— 偏移錯了不會在編譯時報錯，
只會在實機上變成黑畫面，而且症狀跟「根本沒燒進去」一模一樣。選單封面圖
`assets/RetroDict.ino.RAW` 也會一起複製過去，兩個檔案都要放 SD 卡**根目錄**。

一般版（連結在 `0x10000000`，會蓋掉載入器，只適合單獨測試）：

```bash
build_uf2.bat [arduino-cli 的路徑]
```

產出 `build/RetroDict.ino.uf2`。板子端邏輯全部住在 `firmware/`，
`RetroDict/src/rd_*.c` 只是一行 include —— 所以**在 PC 上驗過的程式碼與板子上
跑的是同一份**。SD 卡要有 `/DICT/`（`EC.IDX`、`EC.DAT`、`ECC.IDX`、`FONT.BIN`），
產生方式見 HANDOVER。

## SD 卡

FAT16/FAT32，第一個分割區：

```
SD:\
├── DICT\                    EC.IDX / EC.DAT / ECC.IDX / FONT.BIN
│                            （漢英另外要 CE.IDX / CE.DAT）
│                            FONT.BIN 收的是**字典與注音碼表實際用到的字**，
│                            不是整套 CJK —— 約 1.2MB
├── RetroDict.ino.uf2        給載入器選單
└── RetroDict.ino.RAW        選單封面，檔名要跟 uf2 對上
```

載入器只掃根目錄、封面圖是「uf2 檔名去掉 `.uf2` 再接 `.RAW`」。

## 字典資料從哪裡來

兩個開放資料集，各自負責一個方向。repo 不含它們（體積大、授權要各自遵守），
下載指令見 HANDOVER.md。

| | 來源 | 授權 | 提供什麼 |
|---|---|---|---|
| 英漢 | [ECDICT](https://github.com/skywind3000/ECDICT) | MIT | 770,611 詞條、**218,065 筆 IPA 音標**、詞頻（柯林斯／BNC／FRQ）、詞性、考綱 tag |
| 漢英 | [CC-CEDICT](https://www.mdbg.net/chinese/dictionary?page=cedict) | CC-BY-SA | 124,889 詞條，**每條同時給繁體與簡體詞頭**、拼音 |

### 為什麼是這兩個

**ECDICT 的音標欄位是整台機器的地基。** 這台字典機不做 g2p —— 沒有
letter-to-sound 引擎在猜英文怎麼唸，也沒有錄音檔。它是拿字典裡現成的音標
直接餵給共振峰合成器（`docs/FORMAT.md` §4.2）。當初專案最大的三個未知數
（錄音授權、英文合成器選型、flash 空間）是被「字典本身就附發音資訊」這**一個**
發現一起關掉的。

所以評估任何替代資料集時，第一個問題不是「釋義好不好」，而是**有沒有 IPA**。
沒有的話發音就退回 `firmware/lts.c` 的字母規則推測 —— 那是查不到音標時的
降級路徑，不該變成主路徑。

**CC-CEDICT 的繁簡雙詞頭讓漢英那半是繁體的。** 它每條都同時給繁體與簡體，
所以 CE 的索引鍵與詞頭用繁體、簡體降級成 `SIMP` 欄位 —— 那是**選欄位**，
不是轉換。

### 為什麼英漢的釋義是簡體

**因為 ECDICT 沒有繁體。** 掃過全部 770,611 筆：「电」出現 31,564 筆、
「電」0 筆；「学」12,555 筆、「學」0 筆。不是轉檔時丟掉的。

**那為什麼不用 opencc 轉？** 試過，錯誤是系統性的而不是零星的：光是人名／
地名條目裡的「里」就有 **694 筆**被錯轉成「裡」（`阿尔伯里克` → `阿爾伯裡克`），
`s2t`／`s2tw`／`s2twp` 三種模式全錯 —— opencc 沒有「這是音譯名」的資訊。
而這是 77 萬筆、不會有人逐條校對的資料。幾千筆散落的錯字比簡體字更傷。

（字型不是障礙：EC 釋義用到 6,054 個漢字，其中 5,925 個已經在 CE 的字集裡，
`FONT.BIN` 早就兩套都收了。）

### 為什麼不換一套繁體的英漢資料

量過三條路：

- **反轉 CC-CEDICT 當英漢用** —— 最常用 5,000 詞涵蓋 77.4%，但**全部有音標的
  218k 詞只涵蓋 8.4%**，而且反查出來是詞對詞，沒有詞性與義項，內容會變薄
- **拿 CC-CEDICT 的繁簡詞對當轉換表**（人工維護，比 opencc 精準）—— 只覆蓋得了
  常用詞釋義的 **60.2%**，剩下四成還是得回去用 opencc
- **換掉 ECDICT** —— 目前已知同時有「繁體 + IPA + 可用授權」的只有英文
  Wiktionary，但它是條目化的維基文本而不是整齊的 CSV，移植等於重寫整條
  `tools/dictbuild/build_ec.py`，而且賭上發音這個地基

而真正是簡體的只有 **EC 的釋義文字**這一個欄位 —— 索引鍵是英文、音標是 IPA、
漢英那半是繁體、注音輸入是繁體、介面是繁體。為了一個欄位換掉整個資料地基，
風險不成比例。

完整的數字與推導在 `HANDOVER.md` 的「已定案，不要再翻案」。
