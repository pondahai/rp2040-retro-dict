# rp2040-retro-dict 計畫書

日期：2026-08-23
狀態：規劃階段，尚無程式碼。

---

## 1. 目標

在既有的 RP2040 掌機硬體上做一台電子字典：

- 英漢 / 漢英雙向查詢
- 中英文都能發音，音色刻意做成 1980 年代電子字典那種合成腔
- 字典大資料放 SD 卡，韌體只放程式與必要索引
- 作為 rp2040-retro-loader 選單裡的第 N 支韌體，與 Doom / InfoNES / PicoApple2 共存

---

## 2. 已知條件（已查證）

### 2.1 硬體

沿用生態系共用骨架，本專案不新增任何零件。

| 用途 | 規格 / 接腳 | 來源 |
|---|---|---|
| MCU | Raspberry Pi Pico (RP2040)，可超頻 ~250MHz | 生態系共用 |
| 顯示 | ILI9341 320×240，**spi0**；SCK18 MOSI19 CS17 DC20 RST21 BL22（無 MISO） | PicoApple2-KeyboardTester README |
| 鍵盤 | 8×8 矩陣 64 鍵，74HC595 驅動列 / 74HC165 讀行；DATA_OUT15 LATCH14 CLOCK26 DATA_IN27 | 同上 |
| SD 卡 | **spi1**；CS13 SCK10 MOSI11 MISO12 | rp2040-ili9341-infones README:248 |
| 音訊 | 1-bit PWM → RC 低通 → PAM8403 → 喇叭 | 生態系共用 |

**關鍵：三條週邊互不衝突。** LCD 與 SD 在不同 SPI 匯流排，矩陣用獨立 GPIO。
「讀 SD → 畫面更新 → 放聲音」可以同時進行，不必分時共用。

### 2.2 鍵盤是完整打字鍵盤

64 鍵 = 5 列 × 13 格（SPACE 佔兩格）。完整 QWERTY + 數字列 + 標點 +
SHIFT/CTRL/FN/ALT + 方向鍵 + ENTER/BS/DEL/TAB/ESC。

英文單字直接輸入；中文走拼音也可直接輸入。這是本計畫可行的前提之一 ——
若只有 D-pad，字典會難用到不值得做。

**必須使用 PicoApple2-KeyboardTester README 裡那張實測真值表，
不要抄 `PicoApple2.ino` 的 `keymap_base`。** 舊表已被實測證明有：

- 4 組錯位：S/X 對調、`/`↔PGUP、`=`↔PGDN
- 2 個孤兒：TAB(`[0][6]`,值206)、CAPS(`[2][7]`,值208) 會把原始值當 ASCII 送出
- DEL(`[4][7]`) 未定義，按下去不送東西

遊戲很少按 `/`，查字典會一直按 —— 這些 bug 在字典上會立刻浮現。

矩陣佈局規律：奇偶列交錯，r0/r4 數字、r1/r5 上排、r2/r6 中排、r3/r7 下排，
col 5–7 集中放修飾鍵與功能鍵。

`FN+1~9` = F1~F9、`FN+0` = F10 已是既有慣例，模式切換沿用即可。

### 2.3 中文輸入：注音（已定案）

中文輸入**必須是注音符號**，不做拼音。使用者端已有實作，來源是
`pico_keyboard_ime_terminal`（兩階段二分搜尋查詢 + PROGMEM 字型渲染）。

**大千（標準）注音鍵盤佈局與這把鍵盤相容，不需要任何重新映射。**
對照 KeyboardTester 實測真值表逐一檢查，大千所需的按鍵全部存在：

- 數字列 `1`–`0` ✓
- 三排字母 `q`–`p` / `a`–`l` / `z`–`m` ✓
- 標點 `-` `;` `'` `,` `.` `/` ✓
- 聲調鍵（`6`=ˊ、`3`=ˇ、`4`=ˋ、`7`=˙、SPACE=一聲）✓

37 個注音符號 + 4 個聲調符號都落在既有鍵位上。這是 64 鍵完整鍵盤帶來的直接好處
—— 若當初只有 D-pad，注音輸入根本不可能。

注意 §2.2 提到的錯位在這裡會咬人：`/` 實際在 `[7][4]` 而舊表寫成 213(BTN0)，
按下去什麼都不送。而 `/` 在大千佈局上是 **ㄥ**，是高頻符號。
再次確認：**必須用實測真值表**。

### 2.4 效能餘裕（估算）

| 項目 | 估算 | 結論 |
|---|---|---|
| 查詢延遲 | 12 萬詞條二分搜尋 ≈ 17 次 SD seek × 512B 扇區 ≈ 20–50ms | 使用者感覺是瞬間；不需索引進 RAM，不需 B-tree |
| RAM | 264KB。實際只需當前詞條數 KB + 螢幕緩衝 + 字型快取（一頁約 300 字 × 32B = 10KB） | 完全不緊張 |
| PWM 音訊 | 250MHz 下 8-bit PWM 載波 ≈ 977kHz，遠高於可聽頻段 | 22kHz 取樣用 DMA 餵，CPU 幾乎閒著 |
| 中文音節庫 | 1300 音節 × 400ms × 8kHz × 4-bit ADPCM ≈ 2MB | SD 卡上不算什麼 |

### 2.5 字典資料來源（授權已查證）

| 用途 | 來源 | 規模 | 授權 |
|---|---|---|---|
| 英漢 | [ECDICT](https://github.com/skywind3000/ECDICT) | 基礎版約 76 萬詞條 | **MIT** |
| 漢英 | CC-CEDICT | 約 12 萬詞條 | CC-BY-SA |

ECDICT 額外附帶考綱標註（CET-4/6、IELTS、TOEFL）、Collins 星級、Oxford 3000、
BNC/COCA 詞頻、動詞變化 —— 對電子字典是白送的加分功能（例如「只背 TOEFL 詞彙」）。

**絕對不使用商業字典資料。** 那會讓整個 repo 沒辦法公開。

### 2.6 中文發音不需要 g2p 引擎

原本預期最難的是「漢字→拼音」（要大對照表 + 多音字消歧）。
**這個問題自動消失**：ECDICT 與 CC-CEDICT 的每筆詞條本來就附帶拼音含聲調。
使用者查的詞，字典已經告訴你怎麼念。

```
查詢 → 從 SD 讀出詞條（內含拼音）→ 拆音節 → 拼接音節取樣 → PWM
```

不需要 g2p、不需要多音字消歧、不需要對中文做共振峰合成（聲調會很難聽）。

### 2.7 授權連鎖

PicoApple2-KeyboardTester 是 **GPL-3.0**，`TFT_DMA.cpp/.h` 取自 PicoApple2。
若重用鍵盤掃描 + TFT_DMA（應該重用，那是這台機器最成熟的兩塊），
**本專案就是 GPL-3**。

連帶效果：

- CC-CEDICT 的 CC-BY-SA 資料放 SD 卡，與韌體屬各自獨立作品的聚合（aggregation），不構成衍生

### 2.9 loader 整合規格：最終產物**必須**是偏移版

這不是可選項，是硬性需求。理由有三層：

1. **RP2040 的 bootrom 只認 flash 最前面 256 bytes**，所以 loader 必須住在
   `0x10000000`。每個要被 loader 載入的專題都得讓開，本體從 `0x10004000` 開始。
2. **loader 燒錄時會丟掉 `target_addr < 0x10004000` 的 block**
   （`loader/flasher.c`）—— 那是 loader 自己的地盤，寫下去等於自殺。
   所以一份沒改過的 uf2 放進 SD 卡，前面的區塊會被靜靜丟掉，
   `0x10004000` 什麼都沒有，開機直接死。
3. **RP2040 跑 XIP，每個位址在編譯時就烙進機器碼**。搬檔案、改檔名、
   改燒錄位址都沒用，映像必須重新連結。

這在早期是個難查的坑（失敗症狀與「沒燒進去」無法分辨），
但**已由 `check_flash_layout.py` 解決** —— 它在 build 期驗證向量表確實落在
`0x10004000`、SP/Reset 通得過 loader 的 `app_present()`、UF2 連續、
image 尾端沒越界。照著現成流程做就不會再遇到，**每次 build 都跑它**即可。

而字典正是最需要共存的那種韌體：使用者不會為了查一個單字而拔電按 BOOTSEL。
它天生就該是 loader 選單裡的一項。

實作規格：


- 韌體必須連結到 `0x10004000`，前 16KB 留給 loader / 跳板
- linker script 由 `loader_offset/gen_app_ld.py` 從 arduino-pico 自己那份生成，**不要手改**
- `check_flash_layout.py` 驗證向量表確實落在 `0x10004000`
- 選單封面圖：`<uf2 檔名去副檔名>.RAW`，96×96 RGB565 big-endian、無標頭、**固定 18432 bytes**（loader 只用檔案長度驗證）
- SD 卡**根目錄**，不支援子目錄

## 3. SD 卡的角色與資料配置

SD 卡在本專案的份量比生態系其他韌體重得多。Doom / InfoNES 是「開機讀一次
ROM 就不管了」，**字典是整個生命週期都在讀 SD**。

### 3.1 兩層規則要分清楚

**第一層 —— loader 階段（字典還沒跑）。** 規則由 loader 定，不能改：

- `rp2040-retro-dict.ino.uf2` — 偏移版韌體本體
- `rp2040-retro-dict.ino.RAW` — 選單封面，96×96 RGB565 big-endian、固定 18432 bytes
- **必須放根目錄**，檔名 = UF2 去副檔名再接 `.RAW`

**第二層 —— 字典執行期。** 這裡規則由我們自己定。
**根目錄限制是 loader 的限制，不是 FatFs 的** —— 字典跑起來後用自己的 FatFs，
可以自由用子目錄。資料應收在 `/DICT/` 底下，不要污染根目錄：
同一張卡還住著 Doom 的 WAD、NES ROM、Apple II 的 `.DSK`。

### 3.2 SD 上放什麼

| 內容 | 估計體積 | 性質 |
|---|---|---|
| 英漢索引 + 內文（ECDICT，76 萬詞條）| 未量測 | 唯讀，熱路徑 |
| 漢英索引 + 內文（CC-CEDICT，12 萬詞條）| 未量測 | 唯讀，熱路徑 |
| 16×16 CJK 點陣字 | ~640KB | 唯讀，每次畫面更新都讀 |
| 中文音節庫 ADPCM | ~2MB | 唯讀，按發音鍵才讀 |
| 生字本 / 查詢歷史 / 設定 | 幾 KB | **唯一需要寫入的** |

**英文合成器不放 SD。** SAM 那類是規則式的，資料很小，且在發音熱路徑上 ——
放 flash，2MB 塞得下。

**字型快取不放 SD。** 每個字元都去讀一次扇區會拖慢捲動。
當前畫面用到的字（一頁約 300 字 × 32B = 10KB）快取在 RAM，264KB 綽綽有餘。

### 3.3 三個現在就該定下的設計點

**① 索引必須對齊 512B 扇區。**
二分搜尋每次 probe 讀一個扇區。若索引記錄是變動長度、會跨扇區邊界，
一次 probe 可能變成讀兩個扇區 —— 17 次 seek 直接變 34 次。
把索引做成**固定寬度陣列**（詞頭前 N bytes + 內文偏移量），
讓每次 probe 剛好落在單一扇區內。**這是免費的兩倍效能。**

**② 寫入是唯一的風險來源。**
讀 SD 壞不了東西，寫會。生字本若用「讀出整檔 → 改 → 寫回」，
斷電或抽卡時會整檔毀掉。應做成 **append-only 記錄檔**，只往後追加，
開機時重播。**前提假設：掌機沒有關機流程，使用者就是直接拔電。**

**③ 沒有 SD 卡時的行為。**
Doom 沒卡還能跑（韌體自帶 WAD），**字典沒卡等於完全不能用，連字型都沒有**。
必須有一個不依賴 SD、寫死在 flash 的最小 ASCII 錯誤畫面 ——
否則會黑屏，看起來就像燒錄失敗。

### 3.4 匯流排上的好消息

**SD 在 spi1、LCD 在 spi0，兩條匯流排獨立**（見 §2.1）。
「一邊從 SD 串流音節、一邊更新畫面」不會互相卡住 ——
對「發音時同步高亮當前音節」這類效果是有利的。

## 4. 架構原則：後台與前端必須分離

**這是硬性架構要求，不是風格偏好。**

前提認知：**畫面佈局在開發過程中會大量變動。** 320×240 要塞下查詢框、
詞條、音標、多個義項、例句、注音候選字窗，版面一定會反覆重排 ——
16×16 還是 11×11 沒定（D3）、要不要顯示考綱標註沒定（D4）、
注音候選窗怎麼跟結果頁共存也沒設計。

如果查詢邏輯與畫面繪製糾纏在一起，每次改版面就要動到字典引擎，
**改到後來沒有人敢動版面**。

### 4.1 分界線畫在哪

```
┌─────────────────────────────────────────┐
│  前端 (UI)                                │
│  版面常數、繪製、捲動、輸入焦點、注音候選窗顯示  │
│  ── 唯一可以呼叫 TFT_DMA 的一層 ──          │
└───────────────▲─────────────────────────┘
                │  結構化資料（不是格式化過的字串）
┌───────────────┴─────────────────────────┐
│  後台 (Engine)                            │
│  SD 存取、索引二分搜尋、詞條解析、注音 IME、   │
│  英文合成、中文音節拼接、生字本                │
│  ── 完全不知道螢幕存在 ──                   │
└─────────────────────────────────────────┘
```

### 4.2 三條不能破的規則

**① 後台回傳結構化資料，不回傳排版好的字串。**
`lookup()` 應該回傳「詞頭、音標、拼音、義項陣列、詞性、考綱標記」這樣的結構，
**不是**已經斷好行、填好空白的字串。斷行是前端的事，因為只有前端知道
一行有幾個字。

**② 分界線以下不得出現任何繪圖呼叫、任何座標、任何顏色。**
後台不知道 TFT_DMA 存在。發音模組也一樣 —— 它輸出 PCM，不負責高亮音節；
高亮是前端拿著「目前播到第幾個音節」這個數字自己畫。

**③ 版面常數只准住在前端。**
每行幾字、每頁幾列、字型高度、邊界留白 —— 這些數字如果洩漏到後台，
分離就已經失敗了。

### 4.3 這樣做換到什麼

**最大的回報是後台可以在 PC 上測試，不需要硬體。**
索引格式對不對、二分搜尋有沒有邊界錯誤、詞條解析有沒有吃掉欄位、
音節拼接聽起來如何 —— 這些全部可以在桌機上跑完再燒進板子。

生態系裡已有前例：PicoApple2 用 `src/boot_test.rs` 做全系統開機模擬，
在主機端就驗證出「loader 每讀一個磁區就關開馬達」這種時序 bug。
同一招在這裡更划算，因為字典後台**沒有任何即時性需求**，
比模擬 6502 時序好測得多。

次要回報：版面可以隨便重畫，不會碰到引擎；
U3（音節拼接自然度）那個實驗可以在完全沒有 UI 的情況下先做。

**本節已於 2026-08-23 依實作結果改寫。** 原始版本的幾項假設已被推翻，
推翻的理由本身就是設計依據，所以並列在下面。

第一版：

| 項目 | 現在的做法 | 原本規劃 | 為什麼改 |
