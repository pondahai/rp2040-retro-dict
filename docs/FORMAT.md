# 字典檔格式規格 v1

日期：2026-08-23
狀態：**設計定稿，尚未實作**。對應 PLAN.md §3.3、§6.3 第一項。

這份文件回答 PLAN.md 留下的三個問題：索引結構、內文壓縮、兩個查詢方向
如何共存。讀之前請先讀 PLAN.md §3（SD 卡角色）與 §4（前後台分離）。

---

## 0. 三個決定，先講結論

| 問題 | 決定 | 理由 |
|---|---|---|
| 英漢 / 漢英如何共存 | **分檔，但共用同一套容器格式** | 兩邊詞條數、鍵編碼、欄位都不同；分檔讓讀取器只寫一份、資料各自重建互不影響 |
| 索引結構 | **32 bytes 固定寬度記錄**，前 24 bytes 存截斷鍵 | 512 / 32 = 16，每扇區剛好 16 筆、永不跨界。PLAN §3.3① 要的「免費兩倍效能」 |
| 內文壓縮 | **v1 不壓縮** | SD 是 GB 級，內文大小不是瓶頸；壓縮要換 RAM 與解碼時間。格式留了旗標位，之後要加不必改索引 |

「不壓縮」是有意識的取捨，不是偷懶：本專案的稀缺資源是 **RP2040 的 264KB
RAM 與 seek 次數**，不是 SD 容量。

---

## 1. 檔案配置

全部放在 SD 卡的 `/DICT/` 子目錄（loader 的根目錄限制只管 uf2，執行期讀
子目錄不受限 —— 見 PLAN §3.1）。

```
/DICT/
  EC.IDX      英漢索引（鍵 = 英文詞，ASCII 小寫）
  EC.DAT      英漢內文
  CE.IDX      漢英索引（鍵 = 漢字詞頭，UTF-8）
  CE.DAT      漢英內文
  SYL.PAK     音節音檔庫（另行規格，此處只定義它被 DAT 引用的方式）
  FONT.BIN    點陣字型（另行規格）
```

四個字典檔缺一不可；缺任何一個 → 走 PLAN §3.3③ 的「寫死在 flash 的最小
ASCII 錯誤畫面」，並明確印出缺哪個檔，不要只說「無 SD 卡」。

所有多位元組整數一律 **little-endian**（與 RP2040 原生一致，讀進來直接
memcpy，不做位元組交換）。

## 2. `.IDX` 索引檔

### 2.1 檔頭（第 0 扇區，512 bytes）

| 偏移 | 型別 | 欄位 | 值 / 說明 |
|---|---|---|---|
| 0x00 | char[8] | magic | `"RDICTIDX"` |
| 0x08 | u16 | format_version | 1 |
| 0x0A | u16 | rec_size | 32（固定，讀取器應驗證） |
| 0x0C | u32 | rec_count | 索引記錄總數 |
| 0x10 | u8 | key_encoding | 0 = ASCII 小寫、1 = UTF-8 |
| 0x11 | u8 | direction | 0 = EC（英→漢）、1 = CE（漢→英） |
| 0x12 | u16 | flags | bit0 = DAT 已壓縮（v1 恆為 0） |
| 0x14 | u32 | dat_size | 對應 `.DAT` 的位元組數，開機時比對防錯配 |
| 0x18 | u32 | build_epoch | 轉檔時間，僅供顯示 |
| 0x1C | char[32] | source_tag | 例：`"ECDICT-2018-05"`，授權標示用 |
| 0x3C | u8[452] | reserved | 全 0 |

**檔頭獨佔第 0 扇區**，索引記錄從第 1 扇區開始。因此第 `i` 筆記錄位於
`512 + i*32`，扇區號 = `1 + i/16` —— 對齊性質不因檔頭而破壞。

### 2.2 索引記錄（32 bytes，固定）

| 偏移 | 型別 | 欄位 | 說明 |
|---|---|---|---|
| 0x00 | u8[24] | key24 | 正規化鍵的前 24 bytes，不足補 `0x00` |
| 0x18 | u32 | dat_offset | `.DAT` 中的位元組偏移 |
| 0x1C | u16 | dat_len | 該筆記錄長度 |
| 0x1E | u16 | rank | 排序權重（見 §5），0 = 未知 |

記錄以 `key24` 的 **無號位元組序**（`memcmp` 序）遞增排列。

### 2.3 為什麼是 24 bytes

- EC：24 個 ASCII 字元。ECDICT 絕大多數詞條在此以內，超長者（片語）會被
  截斷成同鍵鄰居，由 §3.3 處理。
- CE：24 bytes = **8 個漢字**。CC-CEDICT 詞頭極少超過 8 字。

截斷不是錯誤，是有意設計：索引只負責把二分搜尋收斂到一小段，
**最終比對用的是 `.DAT` 裡的完整鍵**。

## 3. 查詢演算法

### 3.1 正規化（PC 端與 MCU 端必須完全一致）

EC 方向：轉小寫 → 去頭尾空白 → 內部連續空白壓成單一 `0x20` → 只保留
`[a-z0-9 '.-]`，其餘丟棄。

CE 方向：UTF-8 原樣，僅去頭尾空白。**不做繁簡轉換**（v1 限制，記在 §6）。

正規化規則的實作必須是後台的一個純函式，PC 轉檔工具與韌體共用同一份邏輯；
兩邊不一致會讓查詢靜默失敗，這是本格式最容易踩的坑。

### 3.2 二分搜尋

對 **扇區** 而非對記錄二分：

1. `lo = 1`, `hi = 1 + (rec_count-1)/16`（扇區號）
2. 讀 mid 扇區（512B，一次 SD 讀取），取其中第 0 筆與第 15 筆的 `key24`
3. 目標若落在區間內 → 在這 16 筆中線性掃描；否則調整 lo/hi

76 萬詞條 → 47500 扇區 → **約 16 次 SD 讀取**，而非 20 次記錄級 probe 且
每次可能跨兩扇區。這就是 PLAN §3.3① 說的兩倍。

**已實測**（`tools/tests/test_roundtrip.py` 的合成資料，非估算）：

| 詞條數 | 平均讀取 | 最壞 |
|---|---|---|
| 12 萬 | 13.6 次 | 15 次 |
| 76 萬 | 16.4 次 | 18 次 |

前提是讀取器保留**一個 512B 單扇區快取**。沒有快取的話會多 2–3 次
（二分收斂後會把同一個扇區再讀一遍），韌體實作不要漏。

實作時注意：這裡的二分搜尋要找的是「**最後一個**首筆 ≤ 目標的扇區」，
不是「第一個首筆 ≥ 目標的扇區」。後者會在目標落於扇區中間時整個跳過該扇區，
症狀是「查得到某些字、查不到它旁邊的字」—— 參考實作在這裡踩過一次。

### 3.3 截斷鍵的收斂

找到第一筆 `key24` 相符的記錄後，**向後線性掃描**所有 `key24` 相同的記錄，
逐一讀 `.DAT` 取完整鍵比對。同鍵鄰居通常 1–3 筆，最壞情況（如大量以同一
長片語開頭的詞條）需限制掃描上限為 64 筆後放棄並回報「找不到精確符合，
以下為近似結果」。

### 3.4 前綴查詢（邊打邊查）

使用者每打一個字元，就用當前輸入做一次 §3.2 的 **lower-bound** 搜尋，
取其後連續 N 筆（N = 畫面可顯示列數）作為候選清單。
不需要額外索引結構 —— 排序本身就是前綴索引。

## 4. `.DAT` 內文檔

無檔頭，從偏移 0 起直接是記錄序列。記錄不需對齊（讀取器已由索引拿到
精確 offset/len，一次讀完）。

```
記錄 = u16 rec_len          // 含本欄位自身
       u8  key_len
       u8  key[key_len]     // 完整正規化鍵，供 §3.3 比對
       欄位序列，直到 rec_len 用盡

欄位 = u8  tag
       u16 len
       u8  data[len]
```

未知 tag **必須跳過而非報錯** —— 這是格式向前相容的唯一機制。

### 4.1 欄位 tag 表

| tag | 名稱 | 方向 | 內容 |
|---|---|---|---|
| 0x01 | HEADWORD | 兩者 | 原始詞頭（未正規化，UTF-8），顯示用 |
| 0x02 | PHONETIC | EC | 音標字串（UTF-8） |
| 0x03 | PINYIN | CE | 帶調數字拼音，如 `ni3 hao3` |
| 0x04 | TRANS_ZH | EC | 中文釋義，多義以 `\n` 分隔 |
| 0x05 | DEF_EN | 兩者 | 英文釋義，多義以 `\n` 分隔 |
| 0x06 | POS | 兩者 | 詞性標記字串 |
| 0x07 | EXCHANGE | EC | 詞形變化（ECDICT `exchange` 欄原樣） |
| 0x08 | FREQ | EC | 6 bytes：u16 collins/bnc 名次 ×3，0 = 無 |
| 0x09 | SYL_EN | EC | 英文發音音節 id 陣列（u16 ×n） |
| 0x0A | SYL_ZH | 兩者 | 中文發音音節 id 陣列（u16 ×n） |
| 0x0B | TRAD | CE | 繁體詞頭（CC-CEDICT 同時給繁簡時） |

### 4.2 發音資料在轉檔期就算好

`SYL_EN` / `SYL_ZH` 存的是 **`SYL.PAK` 的音節索引**，不是拼音字串。

也就是說：拼音 → 音節 id 的對照、三聲變調、輕聲處理，全部在 **PC 端轉檔
工具**做完。韌體拿到的是一串 u16，直接餵給播放器。

這條規則的價值：
- 韌體端沒有拼音解析器，省 flash 也省 bug
- 變調規則要改 → 重跑轉檔工具，不必重燒韌體
- **PLAN §4 的前後台分離在資料層也成立**：查詢後台回傳的是 id 陣列這種
  結構化資料，不是排版好的字串

如果 U3（音節拼接自然度）實驗結論是要改變調策略，改的是 `tools/`，
不是韌體。

## 5. `rank` 欄位

u16，值越小越優先。用途是前綴候選清單的排序 —— 使用者打 `ap` 時
`apple` 應該排在 `apparatus` 前面。

- EC：由 ECDICT 的 `bnc` / `frq` 欄位推導，常用詞得小值
- CE：由詞頭長度與是否為單字詞推導（CC-CEDICT 無詞頻欄位）

`rank` 放在索引裡而非 `.DAT`，是為了讓候選清單排序**不必讀 `.DAT`** ——
一次扇區讀取就拿到 16 筆的鍵與權重。

## 6. v1 明確不做的事

記在這裡，避免之後有人以為是漏掉：

- **不做繁簡轉換**。查繁體字若字典只有簡體會查不到。解法留給 v2（在
  轉檔期把繁體詞頭也加進索引指向同一筆 `.DAT`，成本只有索引變大）
- **不壓縮**（理由見 §0）
- **不支援模糊 / 拼錯校正**
- **前綴候選是字母序，不是常用度序**。索引按鍵排序，`hello` 在字母序上離
  `hel` 有數千筆遠，掃描窗口再大也碰不到它。實測打 `hel` 得到的是
  `helen / helena / held`。加大窗口只是浪費 SD 讀取，治不了本。
  這是 v1 的已知缺陷，兩個解法見 §8
- **`.DAT` 不做完整性校驗**。壞掉的 SD 會讀出垃圾。v2 可在檔頭加 CRC

## 7. 這份格式解鎖了什麼

字典檔格式是 PLAN.md 標記的「唯一擋住開工的設計問題」。定下來之後，
以下工作可以**平行**進行且互不阻塞：

1. `tools/` PC 端轉檔工具（ECDICT/CC-CEDICT → `.IDX`/`.DAT`）
2. 查詢後台（純函式 + 一個 `read_sector()` 介面，可在 PC 上用檔案模擬測試）
3. U3 音節拼接實驗（完全獨立，只需要 `SYL.PAK` 的概念，不需要本格式）

其中 2 的可測性正是 PLAN §4 要的：後台不知道螢幕存在，
測試餵它一個假的 `read_sector()` 就能在 PC 上跑完整查詢。

## 8. 待決：前綴候選要不要「常用詞優先」

§6 記的那個缺陷，有兩條路，成本差很多：

**A. 什麼都不做，接受字母序。**
成本零。而且這其實**接近 1980 年代電子字典的真實行為** —— 它們就是顯示
字母序的連續清單，使用者靠翻頁找。以本專案刻意做復古的定位來說，
這不見得是缺點。

**B. 加一個「常用詞索引」`ECC.IDX`。**
只放 rank 最好的前 N 個詞（N = 2 萬時約 640KB），格式與 `EC.IDX` 完全相同、
可以共用同一份讀取器。查詢時先查它拿常用詞，再接字母序的其餘結果。

- 成本：SD 多 640KB、轉檔多一個輸出、韌體多開一個檔
- 回報：打 `hel` 第一個就是 `hello`

**建議 B**，因為 640KB 在 GB 級 SD 上不算成本，而「打三個字母找不到最常用的
詞」在實際使用上會非常刺眼。但這是產品手感的取捨，不是純技術問題，
所以留給使用者決定。
